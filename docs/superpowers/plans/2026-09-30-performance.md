# Производительность публичного сайта — как мерили и что дала каждая правка

**Задача владельца (30.09.2026):** «сделай сайт максимально производительным». Жалобы: вязкая прокрутка, долгие переходы, долго открывается, тормозит на телефоне. Решения владельца: правки из админки видны сразу после сохранения; шторки (интро и переход между страницами) — вдвое короче; прокрутка колесом — отзывчивее. Не трогать: дизайн, тексты, логику форм, адреса страниц, админку (кроме сигнала «сбрось кэш сайта»).

**Ветка:** `perf` (от `main` @ `b394039`). Каждая цифра ниже снята, а не оценена; «до» — прод со старым кодом, «после» — та же машина и сеть.

## Где и чем мерили

- **Машина владельца:** Windows 11, Intel UHD 730, монитор 100 Гц. Сеть из Душанбе до узла Vercel `arn1` (Стокгольм): ~125 мс туда-обратно, полезная скорость ~2,5–3 Мбит/с, и периодические потери пакетов — загрузка «застревает» на 1–5 с. Эти застревания бывают и у старой, и у новой версии одинаково; поэтому сравниваем медианы, а A/B снимаем вперемешку.
- **Телефон** — эмуляция: 390×844, сенсорный ввод, процессор в 4 раза медленнее (дешёвый Android). Для A/B первой загрузки ещё и сеть 4G по профилю Lighthouse (150 мс, 1,6 Мбит/с).
- **Скрипты** — Playwright (Python), лежали в scratchpad сессии, в репозиторий не входят (как и приёмка прошлых этапов). Что они делают, чтобы повторить:
  - *первая загрузка* — свежий браузер на каждый заход, медиана из 5: TTFB, FCP, LCP, «ожила шапка» (у `<header>` появились свойства `__reactFiber…`/`__reactProps…` — React её гидратировал), `load`, байты;
  - *в покое* — счётчики самого браузера через CDP `Performance.getMetrics` за 5 с без движения (TaskDuration, ScriptDuration, RecalcStyleCount…). Свой `requestAnimationFrame`-цикл для подсчёта кадров сюда нельзя: он сам заставляет главный поток работать каждый кадр;
  - *плавность* — кадры через rAF во время прокрутки колесом/пальцем и при наведении на hero, `long-animation-frame`;
  - *отклик колеса* — за сколько мс страница проходит 50/90/99 % пути после одного щелчка колеса;
  - *переходы* — от клика до смены адреса и до появления нового `<h1>`;
  - Lighthouse (mobile + desktop) по семи страницам.
- **Приёмка** после каждого шага — все прежние наборы (концепт, этапы 1–2, формы, Telegram, кейсы, «без рекламы», админка) плюс новые: кэш страниц (48 проверок, в т. ч. «каждый адрес дважды после сброса кэша»), производительные функции (111), «админка → сайт» (11), ссылки на разделы главной (11 на компьютере, 10 на телефоне, и обе раскладки на медленной сети).

## Что было не так (диагноз по замерам)

1. **Каждая страница собиралась на сервере на каждый запрос** (`force-dynamic`) — в функции в Вашингтоне (`iad1`), которая ходила за данными в API в Амстердаме. ~0,4 с серверного времени на каждый документ, на каждый переход внутри сайта и даже на каждый клик по фильтру портфолио (он был переходом на другой адрес).
2. **HTML с сервера не был видимой страницей.** Шапка и многие блоки приходили спрятанными (`opacity: 0`, сдвинуты за экран) и ждали скриптов. На медленной сети страница появлялась только после ~250 КБ JS: «ожила» медианно за 1,5–3,7 с, отдельные заходы — до 11,7 с (в эмуляции телефона — 16,3 с).
3. **Тяжёлый JS на первом экране:** GSAP + Framer Motion + все секции + модалки + форма заявки сразу — First Load JS главной 253 кБ.
4. **Вечные циклы кадров:** Lenis, тикер GSAP, бегущие строки на JS, WebGL-буква на частоте монитора (100 к/с), «магнитные» кнопки. В покое главный поток занят на 11–31 % на телефоне и на 7–17 % на компьютере — даже когда никто ничего не трогает.
5. **Lenis на сенсорных экранах:** его touch-слушатели не пассивные, и каждый свайп ждал главный поток — ровно там, где у телефона его меньше всего.
6. **Ссылки на разделы главной со внутренних страниц** (логотип, «Услуги», «Портфолио», «О компании» в шапке и подвале) были обычными `<a href="/#…">` — полная перезагрузка сайта.
7. **Стили стоят в очереди за шрифтами.** React 19 ставит предзагрузку шрифтов раньше таблицы стилей, CDN отдаёт по порядку — на медленной сети страница пустая, пока не придут ~120 КБ шрифтов, и скрипты до этого даже не запрашиваются (Chrome придерживает низкоприоритетные запросы, пока грузится блокирующий отрисовку CSS). **Не исправлено** — испытанное лечение оказалось хуже болезни, см. «Испытано и откатано».

## Испытано и откатано: CSS внутри HTML

`experimental.inlineCss` кладёт таблицу стилей в HTML — первая отрисовка перестаёт ждать шрифты. Проверено A/B на двух тестовых адресах Vercel, вперемешку, на сети владельца (6 кругов × 6 страниц, медианы):

| | без (A) | с inlineCss (B) |
|---|---|---|
| первая отрисовка | 942–1226 мс | 690–1176 мс (раньше на 0,03–0,39 с на всех страницах) |
| LCP-картинка (главная / кейс) | 954 / 1276 мс | 1916 / 2418 мс |
| «ожила» (5 страниц из 6) | 1148–2033 мс | 2058–2764 мс |
| байт за заход | 385–564 КБ | 429–620 КБ |

Почему хуже: без блокирующего CSS Chrome запрашивает скрипты сразу, и они делят канал с LCP-картинкой; а Next кладёт текст стилей ещё и в каждый RSC-пейлоад (+12,5 КБ сжатого на каждую предзагрузку и переход — вопреки документации), так что одни только предзагрузки шапки добавили 30–56 КБ. HTML вырос на 17–19 КБ сжатого. Откатано (`e65844f`). Если возвращаться к задаче «CSS за шрифтами» — искать способ без дублирования в RSC и без раннего старта скриптов.

## Компромиссы, о которых надо знать

- **На телефонах и планшетах** заголовок hero не анимирует толщину шрифта (перекройка текста каждый кадр стоила ~0,7 с главного потока на слабом процессоре), а шапка и модалки без размытия фона (`backdrop-blur` только с `lg:`). Остальное выглядит так же.
- **Шапка на внутренних страницах предзагружает главную** (~9 КБ сжатого RSC) — обычное поведение `<Link>` в поле зрения; так же уже предзагружались `/smm` и `/vacancies`.
- **Шрифты по-прежнему ~120 КБ** (Manrope и Unbounded, переменные, латиница + кириллица). Урезать без риска для дизайна нечем: каждый текст тянет оба подмножества (пробел и цифры — в латинице).
- **Локальная сборка на Windows не предзагружает шрифты** обычных страниц: в `next-font-manifest-plugin` проверка пути пишется через `/`, и под Windows она не срабатывает (`"app": {}` в манифесте). На Vercel (Linux) предзагрузка есть. Сравнивать загрузку шрифтов — только на Vercel.
- **Буква в hero на компьютере** всё ещё стоит ~8 % главного потока в покое (сам шейдер ~4,9 мс на кадр на UHD 730).

## Как перемерить

1. `npm run build && npm run start` в `frontend/`, API в тестовом режиме (`TELEGRAM_BOT_TOKEN=""`), или тестовый адрес Vercel (`vercel curl` для заголовков; браузеру — заголовок `x-vercel-trusted-oidc-idp-token` только для хоста превью).
2. Первая загрузка: свежий контекст на каждый заход, ≥5 заходов, медианы; A/B — вперемешку, на адресах одного вида.
3. Покой: `Performance.getMetrics` до и после 5 с без действий, без собственных rAF-циклов.
4. Переходы и фильтр: время от клика до `location.pathname === цель` и до нового `<h1>`.
5. Кэш: заголовки `X-Vercel-Cache: PRERENDER/HIT`, `X-Vercel-Id` без второго узла (функция не вызывалась); после `POST /api/revalidate` с токеном админа — каждый адрес дважды отвечает 200.
6. Playwright: каждому контексту — маршрут запросов (`context.route`), иначе `networkidle` под `next start` зависает (см. CLAUDE.md).
